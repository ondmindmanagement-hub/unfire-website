# Unfire OS · P-256 Cross-Language Signed Preview

**Research-only · no persistent key, human authentication, external tools or deployment**

This laboratory proves a narrowly scoped **cryptographic interoperability property**: a P-256 ECDSA/SHA-256 signature generated by Apple's Swift CryptoKit over an exact canonical UTF-8 message can be verified by Node.js `node:crypto`, with the resulting approval consumed once in a SQLite-backed synthetic preview journal.

It does **not** prove that the user's biometric, password, Touch ID, Apple Watch, or macOS identity approved the signature. The test signer uses an **ephemeral, software-only P-256 key generated inside a temporary Swift process**. There is **no Secure Enclave key enrollment, device authentication, Keychain storage, or signed production user consent**. Every successful result has `externalActionAllowed:false`.

## Versioned protocol

This is a **new algorithm version**, not a silent change to the earlier Ed25519 approval research. Never present the two protocols as interchangeable.

P-256 v1 challenge is UTF-8 text, with fields in strict order and one final newline:

```text
UNFIRE-P256-V1
algorithm=ECDSA-P256-SHA256
operation=synthetic.preview
proposalId=<lowercase allowed ID>
proposalDigest=<64 lowercase hex characters>
nonce=<48 lowercase hex characters>
expiresAt=<nonnegative integer milliseconds>
decision=APPROVE
```

The `decision` can instead be `DENY`. A valid approval signature for one decision, proposal, nonce or expiry is not valid for another. IDs, digests, nonces, time and operation are strictly validated, preventing line injection. This is a **research encoding only**; a full external-action protocol would need identity, organization, precise effect/target, cost, policy revision, data classification and executor scope bound to the signed challenge.

Swift signs the **original UTF-8 bytes** with `P256.Signing.PrivateKey().signature(for:)` and exports the ASN.1 DER signature. Node verifies the original bytes with `verify("sha256", ...)` under an **integrator-pinned P-256 SPKI public key**, not one chosen by the language model. No private key or real signing credential is stored by the project.

## State and concurrency gates

The Node `P256PreviewJournal` uses the standard `node:sqlite` API, explicit trusted-host database/clock/key injection and transactional `BEGIN IMMEDIATE` transitions. It supports:

- Model-independent exact-match checks for one of three tiny public synthetic fixtures, rejecting failed model results.
- Fixed `synthetic.preview` operation. Attempts to add mail, payment, browser, app, filesystem or network operations are rejected.
- Per-proposal random nonce, 60-second test expiration and 12-request budget.
- Public verifier key fingerprint pinned in the SQLite journal, with refusal to reopen using another key.
- Atomic single-use consumption, persistent STOP, revocation and last-seen synthetic-clock regression check.
- Audit metadata containing only synthetic IDs, state and sequence; no model raw output, private key, personal prompt or actual tool-use payload.

The state is a **preview-only receipt**; it does not trigger a real task. There is no real model executor, file writer, HTTP request, account access, OS control or external billing in the test code.

## Reproduce on macOS

Use the installed Xcode Swift compiler and Node.js v26. No third-party packages or provider APIs are required:

```sh
node --test experiments/unfire-p256-bridge/protocol.test.mjs
node experiments/unfire-p256-bridge/interop.mjs
```

The second command starts a temporary Swift script. The script prints **only a public verification key**, receives one canonical synthetic challenge from Node, signs it with an ephemeral software key, and exits. Node checks the DER signature, consumes the inert preview once and explicitly verifies replay rejection. The temporary checker exits; it does not create or register a Secure Enclave key or trigger a macOS authentication prompt.

**Observed on the authorized Mac (macOS 27.0.1, Node v26.8.2, Swift 6.4.2):** 15/15 P-256 unit tests passed and cross-language Swift-to-Node handshake succeeded at research SHA `5d2d4be9b16b81036f054aa779df5a8dab9c9f20`. A full combined test run is required on the final source commit before any acceptance. No CI check outcome is claimed.

## Blockers before human-signed production authorization

1. **Trustworthy macOS UI:** only the direct user confirmation action may start protected signing. Screen must display **the exact immutable signed challenge's meaning**, not a model-provided paraphrase.
2. **Secure Enclave P-256 signing:** create and enroll a properly access-controlled key with Apple's Security/CryptoKit APIs. Review `privateKeyUsage`, user-presence/biometry semantics and fallback policy. Do not create keys during unattended tests or store private key material in a repo.
3. **Challenge-to-user binding:** user confirmation and cryptographic signing must share the same context, intended action, policy epoch, expiry and request digest. A standalone `LAContext` success is not a signature.
4. **Identity, enrollment and recovery:** device/user/organization binding, independent verifier registration, key rotation, revocation and legitimate account recovery.
5. **External action sandbox:** a separate narrowly scoped worker with real tool permissions, tested independently, must enforce exact target/arguments, budget and STOP before a real effect.
6. **Durable security and audit:** trusted OS clock, encrypted/key-protected database, rollback and tamper resistance, power-loss recovery, robust concurrency and privacy protections.
7. **Review and CI:** compile/runtime checks on supported macOS versions, adversarial challenge tests, accessibility/security review and a genuine user-driven interaction test.

Apple's official Secure Enclave signing API is `SecureEnclave.P256.Signing.PrivateKey`, but **that API is not called by this experiment**.

**Decision:** Keep this PR DRAFT, UNMERGED and NOT DEPLOYED. Interoperability is proven for this fixed synthetic protocol; real user authentication and external action authorization are not.
