# Unfire OS · Workflow Trace Replay · First Benchmark

**Date:** 31 Oct 2026 · **Environment:** Authorized Mac, Node.js v26.8.2, macOS arm64 · **Status:** Offline synthetic laboratory.

## Purpose and methods

We tested whether **overlapping waiting** helps in a small DAG that resembles a sequence of interdependent AI tasks. The operations are **not AI**: each of 16 jobs combines a deterministic integer hash and optionally a `setTimeout` local delay. A 17th attempt is generated by a deterministic transient failure, so every run includes **one retry**.

All variations use the exact same four independent chains (four stages each) and the same task inputs. Every output is recomputed and checked; a run is accepted only if **16 of 16 digests** match across all lane settings. Each attempt costs eight **invented** credit units, so all runs consume 136 credit units, even when they finish faster. Credits are not actual tokens, money, subscription charges or measured compute energy.

For each of the three workload types and each asynchronous lane count (1,2,4,8), the benchmark runs one unmeasured warmup followed by **four measured repetitions in balanced lane orders**. The times below are per batch, in milliseconds, and include all scheduling, waiting, retry and verification. The CPU calculations remain on a **single JS event loop**, so asynchronous lanes must not be interpreted as hardware processing threads.

## Measured medians (ms, lower is better)

| Workload shape | Wait per stage | 1 lane | 2 lanes | 4 lanes | 8 lanes |
| --- | ---: | ---: | ---: | ---: | ---: |

In the waiting-dominated case, the four-lane median is approximately **3.42× faster** than a one-lane serial replay of this *specific synthetic waiting pattern*. In the mixed case, four lanes are approximately **3.36× faster**. Those ratios **do not describe real AI agent speedups**.

## What was learned

1. **Dependencies matter.** The workflow contains just four simultaneously ready groups, so an eight-lane setting never exceeds four active tasks and adds no genuine concurrency over four lanes.
2. **The fastest measured median is not always the right choice.** The mixed workload's 8-lane median is 46.03 ms vs 47.22 ms for 4 lanes, a difference of only ~2.5%, well within the uncertainty of these few runs. Fewer lanes are preferable absent stable improvement.
3. **Awaiting is not computing.** CPU-only tasks execute serially on one JavaScript thread, despite being labeled as multiple async lanes. The 5.61 ms vs 5.75 ms medians are not proof of parallel CPU speedup; JIT, scheduling and timer noise dominate.
4. **Same correctness and same simulated cost.** 16/16 digest checks, one deliberate retry and 136 abstract credit units in every tested setting. There are no semantic quality measurements and no evidence of lower real token, API or electricity bills.

## Validity limits and deployment gate

This is a tiny experiment with controlled local timers, deterministic hashing, small task batches, and four repeats per configuration. It does not exercise real prompts, tool calls, provider quotas, variable response sizes, rate limiting, external network timeouts, data sensitivity, multiple actual agents, user approval, meaningful model answer quality, process restarts or production observability. It must not be used as proof that any Unfire product is 3× faster.

**Recommendation:** Keep controlled serial execution for short pure computation; consider bounded overlap only for tasks known to spend time waiting and independent of one another. Choose lane count no higher than the verified ready-task parallelism, and require proper real-world measurement before automation. Preserve independent evidence, user permissions, STOP, resource/cost budgets and explicit quality checks. No live AI integration or merge is authorized by this report alone.
